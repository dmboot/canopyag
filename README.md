# canopyag

ROS 2 stack for the canopy.ag SCARA harvesting arm.

- 5x NEMA stepper over CAN (z lift, shoulder, elbow, wrist roll, tool pitch)
- 2x MG996R servo end effector (tool roll + parallel jaws)
- Target: **ROS 2 Jazzy / Ubuntu 24.04 / Gazebo Harmonic**

CAD lives outside this repo in `../../SW/SCARA_V2-Assem/`.

## Why it's shaped like this

Everything goes through **ros2_control**. No bespoke "motor node", no custom
topic protocol between the planner and the drivers. The payoff is that the
URDF, the controllers and MoveIt are byte-identical between simulation and
hardware - the only thing that changes is which hardware plugin the
`<ros2_control>` block names:

```
                MoveIt 2
                   | FollowJointTrajectory
                   v
     joint_trajectory_controller ("arm_controller")
     GripperActionController     ("gripper_controller")
                   |
                   v
          controller_manager  (resource manager)
             /                          \
   sim: gz_ros2_control          real: canopyag_hardware
        GazeboSimSystem                SocketCAN -> 5 steppers
                                       serial    -> 2 servos
```

`sim:=true` vs `sim:=false` on the xacro is the whole switch.

## Build & run

```bash
cd ~/canopyag
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
```

Kinematics check in RViz (fast loop, no physics):

```bash
ros2 launch canopyag_description view_robot.launch.py
```

Gazebo with live controllers:

```bash
ros2 launch canopyag_bringup gazebo.launch.py
ros2 control list_controllers
```

## Where the numbers live

**`src/canopyag_description/config/arm_parameters.yaml` is the only file you
should need to edit** to make the model match the real arm. Link lengths,
joint limits, masses, gear ratios, TCP offset - all of it. The xacro reads
that file; nothing is hardcoded in the URDF.

Every value in it right now is a placeholder that produces a plausible-looking
arm. None of it is measured from your CAD.

## Open question: the 5th NEMA

The chain is reconstructed from CAD part names. Four motors map cleanly (Z
lift via `Z-axisGearbox`, two `ArmSegmentV3` joints on GT2 80T, and
`5to1LastSegment`). The fifth is modelled as `tool_pitch_joint`, a revolute
about Y between the wrist and the tool plate - that's a guess. If it's
actually a gantry rail under the column, a second Z, or part of a
differential wrist, the fix is confined to `arm_parameters.yaml` and
`arm.xacro`; the controllers, launch files and hardware layer are unaffected.

### Note for step 3: 5-DOF IK

The arm has 5 actuated DOF before the gripper, and the default KDL solver
needs 6 to solve a full 6-DOF pose - it will fail on most goals. When you run
the Setup Assistant, pick **`pick_ik`** as the kinematics plugin instead, and
set `approximate_solution: true`. Alternatively generate an IKFast solver for
a 5-DOF configuration. This is a decision to make at Setup Assistant time,
not something to discover when planning silently stops returning solutions.

### Note for step 4: trajectory streaming vs. CAN drivers

`arm_controller` writes a position setpoint every 5 ms. Many CAN stepper
drivers only accept "move to X at speed V" and then run their own trapezoidal
profile, which fights the trajectory and produces stuttering. Before writing
the hardware interface, confirm your drivers accept either a raw position
setpoint at 200 Hz or a velocity command. If they don't, the interface has to
do the profiling itself and expose a velocity interface instead - a different
design, cheaper to decide now than to discover later.
